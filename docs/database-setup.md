# راه‌اندازی پایگاه داده و احراز هویت — مرحله ۳

این سند ساختار پایگاه داده، مدل‌ها، روش راه‌اندازی، متغیرهای محیطی و ملاحظات امنیتی مرحله «حساب کاربری و پروفایل» را مستند می‌کند.

## ۱. انتخاب backend و پایگاه داده

| موضوع | انتخاب | توضیح |
|---|---|---|
| ORM | **Prisma 6** | از ابتدا در پروژه نصب بود؛ تغییر نسخه لازم نبود |
| پایگاه داده | **SQLite** (`db/custom.db`) | PostgreSQL و MySQL در محیط اجرای فعلی نصب نیستند (بررسی شد: `psql`/`postgres`/`mysqld` در دسترس نیستند). SQLite فایل‌محورِ سمت سرور، داده‌ها را به‌صورت **دائمی و واقعی** ذخیره می‌کند و برای این مرحله کاملاً کافی است |
| احراز هویت | **better-auth 1.7.8** | کتابخانه معتبر با نشست دیتابیسیِ قابل ابطال، محدودسازی نرخ داخلی، بررسی Origin و کوکی امن؛ سازگار با Next.js 16 و React 19 |
| هش رمز عبور | **bcrypt (cost = 12)** | با `bcryptjs` پیاده شده و از طریق پیکربندی `emailAndPassword.password` به better-auth وصل است؛ هش در جدول `account` نگهداری می‌شود |

> **مسیر مهاجرت به PostgreSQL:** در `prisma/schema.prisma` مقدار `provider` را به `"postgresql"` تغییر دهید، `DATABASE_URL` را در `.env` به آدرس سرور Postgres تنظیم کنید و `bun run db:push` (یا `prisma migrate`) را اجرا کنید. تنها نکته خاص SQLite، ذخیره آرایه‌ها به‌صورت JSON است که در Postgres می‌تواند به ستون `json`/`text[]` تبدیل شود؛ لایه سرویس (`src/lib/profile.ts`) از این جزئیات جدا است و تغییری نمی‌خواهد.

## ۲. مدل‌های پایگاه داده

```
user (۱) ──── (۱) FitnessProfile      رابطه یک‌به‌یک، onDelete: Cascade
  │
  ├── (n) session    نشست‌های فعال — قابل ابطال با حذف ردیف
  └── (n) account    اطلاعات احراز هویت (providerId = "credential" + hash رمز)
```

### user (قرارداد better-auth)
- `id` (رشته تصادفی امن)، `email` (یکتا، نرمال‌شده به حروف کوچک)
- `name` (نام نمایشی؛ با ذخیره پروفایل همگام می‌شود)، `emailVerified`، `image`
- `createdAt`، `updatedAt`

### account
- `userId` → کلید خارجی به `user` (Cascade)
- `providerId = "credential"` و `password` = هش bcrypt `$2b$12$...`
- فیلدهای OAuth برای آینده خالی مانده‌اند

### session
- `userId` → `user` (Cascade) + `token` (یکتا، هش‌شده در کوکی)
- `expiresAt` (۷ روز)، `ipAddress`، `userAgent`
- **قابل ابطال:** حذف ردیف = خروج فوری آن دستگاه (در خروج و حذف حساب خودکار انجام می‌شود)

### verification
- جدول استاندارد better-auth برای جریان‌های تأیید آینده (تأیید ایمیل/بازیابی رمز — هنوز فعال نیست)

### FitnessProfile
| ستون | نوع | توضیح |
|---|---|---|
| `userId` | یکتا، FK → user | رابطه واقعی یک‌به‌یک با محدودیت پایگاه داده |
| `displayName` | String (الزامی) | نام نمایشی در داشبورد |
| `age` | Int? | ۱۰ تا ۹۰ |
| `gender` | String? | `male / female / undisclosed` — اختیاری، برای فرمول‌های آینده |
| `heightCm` | Float? | ۱۰۰ تا ۲۵۰ |
| `weightKg` | Float? | ۲۵ تا ۳۰۰ |
| `bodyFat` | Float? | اختیاری |
| `goal` | String? | `fat_loss / muscle_gain / strength / maintain / fitness` |
| `experience` | String? | `beginner / intermediate / advanced` |
| `trainingDaysPerWeek` | Int? | ۱ تا ۷ |
| `sessionMinutes` | Int? | ۱۵ تا ۱۸۰ — اختیاری |
| `equipmentJson` | String | آرایه JSON از کدهای تجهیزات |
| `limitationsJson` | String | آرایه JSON از کدهای محدودیت (محرمانه) |
| `limitationNotes` | String? | توضیح آزاد کاربر (محرمانه) |
| `diet` / `allergiesJson` | String? / String | ترجیحات غذایی برای مرحله تغذیه |
| `units` | String | `metric / imperial` |
| `createdAt / updatedAt` | DateTime | |

> چرا فیلدهای بیشتر از حداقل مشخصات؟ چون فرم تأییدشده مرحله ۱ (درصد چربی، مدت جلسه، رژیم و آلرژی) حفظ شده و این فیلدها در مراحل ۶ و ۷ (برنامه تمرینی/تغذیه) لازم می‌شوند؛ همه به‌جز `displayName` اختیاری‌اند و در گزارش‌ها لاگ نمی‌شوند.

## ۳. راه‌اندازی

```bash
# ۱) وابستگی‌ها
bun install

# ۲) اعمال اسکیما به دیتابیس (فایل db/custom.db می‌سازد/به‌روزرسانی می‌کند)
bun run db:push

# ۳) اجرا
bun run dev   # ← توسط محیط به‌صورت خودکار اجرا می‌شود
```

## ۴. متغیرهای محیطی (`.env`)

| متغیر | وضعیت فعلی | نقش |
|---|---|---|
| `DATABASE_URL` | ✅ تنظیم شده (`file:/home/z/my-project/db/custom.db`) | آدرس فایل/سرور پایگاه داده |
| `BETTER_AUTH_SECRET` | ✅ به‌صورت خودکار تولید و تنظیم شده | کلید امضای کوکی نشست — فقط سمت سرور خوانده می‌شود |

برای اتصال به **PostgreSQL واقعی خارجی** (اختیاری، خارج از این سندباکس) فقط این موارد لازم است:
- `DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DBNAME`
- تغییر `provider` در schema و اجرای `db:push`
- هیچ کلید دیگری (سرویس ثالث، SMTP و…) در این مرحله لازم نیست.

## ۵. امنیت — تصمیم‌ها و سیاست‌ها

- **هش رمز:** bcrypt cost 12؛ متن ساده هرگز ذخیره/لاگ نمی‌شود (تأییدشده: `$2b$12$` در دیتابیس).
- **نشست:** دیتابیسی و قابل ابطال؛ عمر ۷ روز با تازه‌سازی روزانه؛ کوکی `fitcoach.session_token` با `HttpOnly` و `SameSite=Lax` (فلگ `Secure` به‌صورت خودکار روی HTTPS فعال می‌شود).
- **نرمال‌سازی ایمیل:** trim + lowercase در هک سمت سرور (برای همه درخواست‌های ورود/ثبت‌نام).
- **سیاست رمز:** حداقل ۸ کاراکتر + حداقل یک حرف و یک رقم (سطح سرور از طریق hook).
- **محدودسازی نرخ (better-auth):** ورود و ثبت‌نام حداکثر **۵ درخواست در ۶۰ ثانیه**؛ سایر مسیرهای auth سقف ۱۰۰ در دقیقه. پاسخ 429 با پیام فارسی.
- **CSRF/Origin:** better-auth مبداهای معتبر را محدود می‌کند؛ برای پشتیبانی از دامنه پیش‌نمایش، مبدأ پویا از هدر `Host` خوانده می‌شود (فقط same-origin). کوکی‌های SameSite=Lax لایه دوم حفاظت‌اند.
- **کنترل دسترسی:** همه APIها (`/api/profile`, `/api/account`) شناسه کاربر را **فقط از نشست** می‌خوانند؛ `userId` ارسالی از کلاینت در شِما وجود ندارد و نادیده گرفته می‌شود (تست شده).
- **بدون افشای خطا:** خطاهای دیتابیس فقط با نام Exception لاگ می‌شوند؛ به کاربر کد عمومی (`INTERNAL`/`VALIDATION`) برگردانده می‌شود.
- **حریم خصوصی در لاگ‌ها:** لاگ کوئری Prisma به `error` محدود شد (مقادیر پروفایل لاگ نمی‌شوند)؛ در هندلرها email/رمز لاگ نمی‌شود.
- **حذف حساب:** `DELETE /api/account` ردیف `user` را حذف می‌کند و Cascade همه داده‌های وابسته (پروفایل، نشست‌ها، account) را پاک می‌کند (تست شد: صفر ردیف یتیم).

## ۶. نقاط پایانی API

| مسیر | متد | توضیح |
|---|---|---|
| `/api/auth/sign-up/email` | POST | ثبت‌نام (better-auth) + ورود خودکار |
| `/api/auth/sign-in/email` | POST | ورود؛ خطای غیرافشاگر 401 |
| `/api/auth/sign-out` | POST | خروج و ابطال نشست |
| `/api/auth/get-session` | GET | وضعیت نشست جاری |
| `/api/profile` | GET | پروفایل کاربر جاری یا `null` |
| `/api/profile` | PUT | ایجاد/به‌روزرسانی پروفایل (اعتبارسنجی Zod سمت سرور) |
| `/api/account` | DELETE | حذف کامل حساب + داده‌های وابسته |

## ۷. محدودیت‌های شفاف این مرحله

- **تأیید ایمیل و بازیابی رمز عبور پیاده نشده‌اند** (نیاز به سرویس SMTP دارد)؛ این وضعیت در خود صفحه ورود هم به کاربر اعلام شده است. جدول `verification` برای آینده آماده است.
- پایگاه داده همین محیط SQLite است؛ PostgreSQL در سندباکس در دسترس نیست (مسیر مهاجرت بالا مستند شد).
- در محیط development (HTTP لوکال) فلگ `Secure` کوکی غیرفعال است؛ روی HTTPS پیش‌نمایش/production خودکار فعال می‌شود.
- هشدار `THREE.Clock` در کنسول از کتابخانه‌های three/drei (مرحله ۲) است و ربطی به این مرحله ندارد.
